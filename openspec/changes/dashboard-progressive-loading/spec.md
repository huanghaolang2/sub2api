# 仪表盘按需加载与模型看板

状态：`SPEC_APPROVED`。已完成两遍自检和修订，用户于 2026-10-26 明确回复“都确认通过，按该 spec 编写一个适合 codex 并发并行开发、快速开发的 plan”，Spec 总体审核通过，正文冻结。无 SQL 变更，不进入 SQL 专项审查。实施方案与任务状态见对应 Plan。

## 背景与现状

目标为 `https://web.chuangyedaosheng.net/dashboard` 对应的个人仪表盘。

- 当前 `frontend/src/views/user/DashboardView.vue` 同时启动周趋势、月趋势和用户累计统计请求，并等待累计统计后才展示趋势组件。
- 使用趋势目前展示最近 4 个自然周的「周看板趋势」和最近 3 个自然月的「月看板趋势」。趋势组件和请求代码分别维护固定的周期列表。
- Token 用量排行按当周、当月、累计展示 API Key；周/月数据来自趋势响应，累计数据来自 `/api/v1/usage/dashboard/stats` 的 `usage_board`。列表已展示全部返回项，但没有固定高度。
- `/api/v1/usage/dashboard/models` 已支持个人权限范围、日期和时区，按请求模型标识聚合，返回完整模型列表及 `total_tokens`。该聚合包含零费用记录，无需新增统计接口或修改 SQL。
- `/usage/board` 的 `series` 包含本次筛选的完整系列，只有 `rows` 受分页影响；当前未限定密钥 ID 时，系列不包含整个查询区间内完全没有记录的密钥，完整密钥名单仍来自累计统计。
- 共享请求层默认超时为 30 秒，且会覆盖 GET 参数中的 `timezone`。本次请求适配需要保证仪表盘显式指定的统计时区实际生效，不能只在调用参数中写入快照值。
- 标准 Dockerfile 构建 `frontend`。`frontend2` 是另一套布局，本次范围限定于与需求描述一致的 `frontend` 个人仪表盘。
- 本次查看目标网址时跳转到登录页，尚未验证线上实际运行版本和登录后的页面；上述实现事实来自当前 checkout。

## 目标与范围

1. 让页面结构和前部趋势先展示，依据实际展示的看板确定数据依赖和加载顺序。
2. 将累计 Token 排行请求延后，周/月 Token 排行复用已经加载的趋势数据。
3. 在 Token 用量排行下方增加模型看板，提供当周、当月、累计三个排行，并延后其请求。
4. 保留既有看板视觉语言、明暗主题、响应式布局与个人数据权限。

不包含后台看板配置管理功能、管理员仪表盘、`frontend2` 改版、计费逻辑、数据库或 SQL 修改、线上部署、Git 提交或推送。工作区已有的网关与 WebSocket 改动不属于本次范围。

## 需求与行为

### FR-001 展示内容决定加载需求

- 看板的展示定义与数据依赖使用同一来源，不能在渲染逻辑和请求调度中分别维护固定的看板名单。
- 依据当前参与渲染的看板定义构造请求；未展示且没有被其他展示看板依赖的数据不请求。增加、移除、重排或调整已有看板的统计周期时，加载需求与其展示定义同步。
- 不新增用户配置界面或持久化配置。这里的「配置」指页面用于声明展示内容、顺序和统计周期的定义。
- 展示定义同时声明看板的加载阶段和数据依赖；调度不能根据标题、固定数组下标或另一个独立维护的周期列表猜测需求。默认前部趋势属于优先阶段，Token 排行和模型看板属于延后阶段。
- 「展示」指页面当前定义中启用并渲染的看板，不以是否处于浏览器可视区域判断。窄屏布局调整不创建第二套请求；隐藏后仍被其他展示看板依赖的数据保留请求，并按剩余消费者所需的阶段加载。
- 相同权限、数据类型、周期、时间范围、时区及其他影响响应内容的参数构成同一数据需求；在一次加载中共享请求和结果。成功结果不因单纯重排重新请求；失败后的明确重试不受去重限制。周/月趋势与对应 Token 排行共享响应。
- 看板类型、周期、加载阶段和加载状态等新增有限业务选项集中定义为枚举。

### FR-002 优先趋势与分阶段加载

- 页面挂载后立即展示主体结构及各区域占位，不以累计统计或用户资料刷新作为趋势区域的显示前提。
- 第一阶段只发起当前展示定义声明为优先的数据请求。默认内容保持周/月趋势及其现有时间范围；调整默认内容时，不能继续请求已经不需要的旧周期。
- 每个趋势独立更新：一个请求完成后即可展示该看板，不等待另一个请求；失败只影响对应区域。
- 优先请求全部结束（成功或已显示错误）且结果已提交页面渲染后，才进入延后阶段，发起累计 Token 排行及模型看板请求。延后请求之间可以并行；它们不能反向阻塞趋势展示。
- 延后加载依赖请求完成及页面渲染事件，不使用固定等待若干秒的定时器判断主体完成，也不要求用户滚动后才能触发请求。
- 当前展示定义没有优先请求时，主体占位完成一次渲染后即可进入延后阶段。优先请求沿用共享请求层的超时与错误处理，超时也视为该请求已结束，不永久卡住阶段切换。
- 页面离开后，不再启动尚未开始的延后请求；取消在途请求并忽略过期响应。展示定义改变后，旧请求不得覆盖新定义的结果，移除看板不得继续启动其专属请求。
- 同一轮加载使用同一份当前日期和时区快照生成有时间范围的趋势及模型请求，并据此选择周/月 API Key 排行所属的周期，避免跨午夜或月初混用不同周期。失败重试保留原轮次范围；重新进入页面建立新的快照。本次不新增跨日自动刷新。
- 快照只固定查询周期，不固定持续变化的数据库内容。累计 API Key 统计接口没有日期参数，沿用其请求执行时的所有保留记录；分阶段返回的数据不承诺来自同一数据库事务或完全相同的采样时刻。

### FR-003 Token 排行固定高度及完整数据

- 保留当周、当月、累计三个 API Key 排行，保持现有总 Tokens 口径、命名、零用量项及排序行为。
- 当周/月优先使用已完成的趋势结果，不重复请求；累计统计成功后必须按 API Key ID 合并完整名单，补齐当周/月未使用密钥的零用量项，并沿用累计名单对同名密钥的区分。累计统计失败时仍展示已成功取得的当周/月排行，并说明完整密钥名单暂不可用，不将其标为完整名单。
- 周/月趋势和排行从完整的 `series` 取数，排行只取所属自然周期的数据点，不累加整个趋势窗口，不从分页 `rows` 推导全量排行；不能因 `page_size` 或可视 20 行的设置漏掉其他 API Key。
- 每个排行卡片内的列表区域固定高度，在桌面端标准字号下可完整显示约 20 行（19–21 行）；卡片标题及日期说明位于滚动区域外。窄屏允许因名称与数值换行减少可视行数，不缩小文字强行容纳 20 行。
- 超过可视高度的项目通过各自区域内纵向滚动查看，不通过截取前 20 项实现。所有返回项目均可到达，包括末项和零用量项。
- 少于 20 项、加载中、空数据和错误状态保留相同列表区域高度，避免加载后页面大幅跳动。
- 窄屏沿用卡片纵向排列；列表仍在卡片内滚动，长名称可截断并提供完整名称提示，Token 数值可读。滚动区域可获得键盘焦点并具有可理解的名称。

### FR-004 模型看板与统计口径

- 在 Token 用量排行下方新增「模型看板」。桌面端三个排行并排，窄屏纵向排列；卡片、间距、字体、Tokens 格式、明暗主题沿用 Token 排行风格。
- 三个排行标题分别为「当周使用 Top」「当月使用 Top」「累计使用 Top」，每项展示名次、请求模型标识和总 Tokens。
- 按当前登录用户的既有模型统计接口聚合结果展示，不扩展到平台所有用户，不改用上游模型或映射后模型。请求模型标识沿用接口的既有历史兼容规则：优先使用非空的 `requested_model`，历史记录缺失时回退到 `model`；不在前端重新聚合或重命名模型。
- 当周从浏览器时区的本周一开始，当月从当月 1 日开始，结束均包含当天；浏览器无法提供时区时使用 UTC。累计使用覆盖现有接口可查询的全部保留历史，显式传入 `0001-01-01` 作为累计起始日期，不能误用接口默认的最近七天。
- 总 Tokens 使用接口的 `total_tokens`，即输入、输出、缓存创建、缓存读取之和。零费用但有 Tokens 的使用记录仍纳入模型用量。
- 模型统计按 `usage_logs.user_id` 归属，沿用接口对保留记录的语义；API Key 看板按当前未删除密钥归属，两者不承诺总量相等。本次不迁移或统一历史数据归属规则。
- 按总 Tokens 降序排序；相同用量按模型标识稳定排序。展示所有返回模型，不静默截断 Top 数量；列表采用与 Token 排行相同的固定高度和内部滚动方式。
- 模型请求仅在 FR-002 的延后阶段开始，不依赖累计 Token 排行成功。各周期独立展示加载、成功、无数据和错误状态。

### FR-005 失败和恢复

- 加载状态区分未开始、加载中、成功与失败；请求失败不能展示为真实零用量或无数据。
- 一个周期或一个区域失败不阻断其他区域，不清除已成功展示的看板。
- 请求失败时在受影响区域显示错误及重试入口；只重试失败的数据依赖，成功的共享请求结果继续复用。同一失败依赖有多个消费者时，重试状态和结果同步更新，不重复发起请求。
- 延后阶段在当前轮次只启动一次。进入延后阶段后重试某项优先数据，不撤回或重复启动其他延后请求；依赖该失败数据的排行随重试结果更新。重复点击正在加载的重试入口不产生并发副本。
- 成功返回空列表显示明确的无数据状态；成功返回零用量保留真实零值。

## 接口、数据所有权与兼容

- 继续使用现有 `/usage/board`、`/usage/dashboard/stats` 和 `/usage/dashboard/models` GET 接口；既有后端参数、响应和鉴权语义保持兼容。前端请求适配范围包含可选的取消信号，以及保证仪表盘显式时区不被自动注入覆盖；其他调用方不传新选项时保持现有行为。
- 日期区间按指定统计时区的自然日解释，结束日期包含当天。界面显示模型排行的实际请求范围，不依赖固定加减 24 小时计算自然日边界，避免夏令时切换造成日期标签偏移。
- 排行与趋势均为只读展示，不改变使用记录、密钥、用户、费用或其他持久化数据；不引入 SQL、迁移、数据库索引或新依赖。
- 请求以登录会话的权限为边界，不在前端指定其他用户身份，不记录或展示完整 API Key 秘密值。
- 新的加载调度只服务于当前仪表盘，不扩展为全站通用看板平台或跨页面持久缓存。

## 验证方式与边界

- 前端组件/调度测试：使用可控的未完成 Promise 检查阶段顺序、独立渲染、共享去重、展示定义变化、失败重试及卸载取消；不以任意延时或最终快照代替请求顺序断言。
- 排行与日期测试：检查完整 `series` 与分页 `rows` 的差异、当前周期选择、完整列表、同名密钥、模型排序、周/月及跨年边界、累计范围、夏令时日期标签及错误/空状态。
- 请求适配验证检查实际交给共享客户端底层适配器的最终参数和取消信号，不能只断言上层函数收到正确的时区。时区获取抛错或为空时显式使用 UTC。
- 对受影响代码运行 Vitest、TypeScript 检查、ESLint，并执行前端构建；仅运行与本次变更有关的测试及项目构建自身要求的检查。
- 本地浏览器核对固定高度、超过 20 行时的内部滚动及末项可达、明暗主题和窄屏布局。受控数据验证可以证明交互与布局，不能代替真实接口验收。
- 零费用记录纳入模型统计的依据是现有服务与仓库聚合实现；前端 Mock 测试只能证明正确展示响应，不能证明真实数据库统计。累计起始日期经当前解析链路静态核对可传入，实际数据库驱动绑定及大数据量下的查询耗时仍列为真实接口待验证事项，不以本地 Mock 代替。
- 实施及计划内验证完成后运行一次只读 `acceptance-audit`，对照本 Spec、冻结 Plan、实际差异和已有验证证据核对验收条件。
- 真实环境待验证：登录目标网址后核对当前部署版本、网络请求瀑布、真实数据权限/模型口径、数据量下的耗时和列表滚动。本地测试与构建成功不代表线上已经部署或验收。

## 已确认调整：模型用量门槛与 Top 10（2026-10-26）

用户明确要求：模型看板不展示每一种模型；当周单模型总 Tokens 必须严格大于 1,000,000，当月和累计单模型总 Tokens 必须严格大于 100,000,000，筛选后各周期最多展示前 10 名。这一补充覆盖 FR-004 和 AC-006 中原先“展示所有模型、超过20项仍可浏览全部”的模型展示要求，其余统计口径、加载顺序和权限不变。

- 比较使用接口的原始 `total_tokens`，不使用格式化后的数字；恰好等于门槛的模型不展示。
- 先按各周期门槛筛选，再按 Tokens 降序和模型标识稳定排序，最后取前10名；不足10个时仅展示符合条件的模型，不补齐低用量模型。
- 没有符合条件的模型时显示“暂无符合展示条件的模型”；页面说明列出门槛和前10名规则。
- 仅调整模型看板。API Key 的 Token 用量排行继续完整展示，保持约20行视口与内部滚动；模型卡片也保留既有视口高度。
- 验收覆盖门槛前一单位、恰好门槛、门槛后一单位，以及超过10个符合条件模型时先排序后截取。无 SQL、接口或持久化变更。
